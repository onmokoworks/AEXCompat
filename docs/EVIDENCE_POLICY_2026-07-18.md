# Evidence Policy Revision (2026-07-18)

Decision owner: repository owner, via direct task response.

Decision: **shift the regression axis from frozen-identity re-assertion to
machine-portable behavioral self-tests, while keeping runtime identity
pinning, native-execution receipts, and claim stratification unchanged.
Runtime worker trust is admission state, not regression evidence: it is
always regenerated by script after a worker rebuild (section 3).**

This document is policy, not an immediate replacement of existing assets.
Existing evidence tests and `analysis/` documents are not deleted or
rewritten by this document; migration happens in staged follow-up changes
after this policy is merged. The only mechanical change shipped with the
policy is the trust-regeneration path it requires
(`tools/refresh-worker-trust.ps1` and the generated trust files).

## 1. The Current Evidence System (Observed)

The repository currently combines four mechanisms:

1. **Runtime evidence JSON in `analysis/`.** Executed probes and workers write
   dated result documents that embed the identity (path, `size_bytes`,
   `sha256`) of the sources, workers, probes, plug-in fixtures, and outputs
   involved. Focused tests re-assert those frozen values against the current
   worktree; for example, `tests/test_pf_sampling_fill_runtime_result.py`
   re-hashes the probe AEX and compares a pinned `output_sha256`.
2. **Worker trust constants in the broker.**
   `broker/crates/broker/src/generated_l2_worker_trust.rs` pins the L2
   worker's SHA-256 and byte size and is generated by
   `tools/refresh-sdk-grabba-evidence.ps1` (the file is marked "Do not edit by
   hand" and is `include!`d by `image_render.rs`). When this policy was
   drafted, `RENDER_WORKER_TRUST` and `SMART_WORKER_TRUST` were embedded
   directly in `broker/crates/broker/src/image_render.rs` with no generator
   script; the change that introduces this policy moves them into generated
   files and adds `tools/refresh-worker-trust.ps1`, which rebuilds all three
   workers and regenerates all three constants (see section 3).
3. **The local-artifact gate.** `tests/conftest.py` reads
   `tests/local_artifact_tests.txt` and skips the listed node ids unless
   `--run-local-artifact-tests` is passed, so a clean clone still runs every
   source-reproducible test.
4. **Refresh runners.** `tools/refresh-runtime-evidence.ps1` rebuilds the
   canonical workers/probes, re-executes the recorded commands, and rewrites
   the identity fields of the named `analysis/` documents from executed
   artifacts. `tools/refresh-sdk-grabba-evidence.ps1` does the same for the
   Grabba AEGP evidence and regenerates the L2 trust constant.

The intent behind this system remains valid: it disciplines agent-driven
development, leaves an audit trail for native-execution escalation, acts as a
next-best substitute for CI in a single-machine environment, and supports the
maturity levels of `docs/PROJECT_DIRECTION.md` (host reproduction is never
silently promoted to AE equivalence).

## 2. Observed Problems

1. **Frozen build hashes bind the repository to one machine.** C++ builds are
   not deterministic across toolchains or machines, so a frozen worker hash
   and the trust constants describe the last machine that regenerated them,
   not the source revision. This has been observed directly: rebuilding the
   worker on a second machine fails the trust-comparison test
   (`tests/test_sdk_grabba_trusted_worker_generation.py`) even though the
   source is identical. Every worker source change requires regenerating both
   the `analysis/` documents and the trust constants, which obstructs
   collaboration across machines.
2. **The frozen assertions verify less than their naming suggests.**
   Source-string marker tests (for example
   `test_l2_source_writes_full_checkout_result` in
   `tests/test_pf_pre_checkout_result.py`) break under behavior-preserving
   refactors and pass under behavior-breaking edits that keep the strings.
   Re-asserting frozen JSON values proves that the JSON has not drifted from
   the worktree, but an edited JSON re-asserts just as green. Words such as
   "audit", "gate", and "authenticate" in test names appear to promise more
   than these checks deliver.
3. **Per-step artifact expectations encourage receipt proliferation.** A
   framework that expects an artifact for every step pushes agent-driven work
   toward near one-to-one `tools/`-to-`tests/` pairing and naming inflation,
   which adds maintenance cost without adding verification strength.

## 3. Runtime Trust Is Not Regression Evidence

The single most important boundary in this policy is the separation of two
things that the previous workflow conflated:

- **Runtime trust (admission state).** The worker trust constants exist so
  that the broker refuses to dispatch through a worker binary it has not
  approved; dispatch fails closed on a hash or size mismatch. This is a
  runtime safety property, and it is **not relaxed**. Any change that
  produces a new worker binary must regenerate the trust constants before
  broker-based execution can work at all, and skipping that step simply
  stops the harness. The regeneration path is `tools/refresh-worker-trust.ps1`
  (all three workers), or `tools/refresh-sdk-grabba-evidence.ps1` when the
  L2 evidence chain is being refreshed at the same time.
- **Regression evidence (frozen records).** The dated `analysis/` documents
  record what a past execution produced. Re-freezing them is meaningful only
  when the recorded execution is actually re-run, so their regeneration is
  tied to the refresh runners, not to every source commit.

A worker source change therefore always implies "rebuild, regenerate trust,
re-run the broker integration tests" and only sometimes implies "re-freeze
evidence". Broker integration testing after a worker rebuild is mandatory:
run `cargo test --manifest-path broker\Cargo.toml --workspace` and exercise a
broker-dispatched render (harness or CLI route) before treating the rebuilt
worker as usable.

## 4. What Is Retained

- **Runtime identity pinning.** The broker continues to hash the selected
  AEX, its dependency manifest, and the worker at dispatch time, and the
  sealed load tree, restricted token, Job Object, timeout, and module audit
  remain mandatory. This policy changes how regressions are verified, not how
  native code is admitted at runtime.
- **Receipts for native-execution escalation.** Crossing a boundary that
  executes new native code still produces a recorded, reviewable receipt.
- **Claim stratification.** "Locally verified", "real AEX verified", and
  "AE-oracle verified" remain distinct levels
  (`docs/PROJECT_DIRECTION.md`), and AE-dependent evidence keeps the strict
  identity contract of
  `docs/AE_ORACLE_CROSS_MACHINE_RUNBOOK_2026-07-18.md`. That runbook already
  treats AE captures as machine-bound (`environment_mismatch` /
  `exact_bind_failure` instead of silent reuse); this policy adopts the same
  stance for host-side builds by not pretending their hashes are portable.

## 5. What Changes

1. **Regression verification moves to behavioral self-tests.** The primary
   regression check for host behavior is a test that any machine can run
   after building the workers from source. The reference shape is
   `tests/test_pf_pre_checkout_result.py`: an SDK `static_assert` compile
   test for the frozen ABI, a contract-level check, and a native self-test
   route (`--self-test-pf-pre-checkout-result`) executed against all three
   workers with a machine-independent pass verdict. "Machine-portable" means
   portable across machines that build the workers from source, not runnable
   from a clean clone: self-tests need built binaries, so they are listed in
   `tests/local_artifact_tests.txt` and skipped by a plain
   `python -m pytest -q`. Changes that touch worker or host behavior must be
   verified with `python -m pytest -q --run-local-artifact-tests` on a
   machine with built workers.
2. **Frozen-value verification runs only at regeneration time.** Evidence
   documents are updated exclusively through the refresh runners
   (`tools/refresh-runtime-evidence.ps1`,
   `tools/refresh-sdk-grabba-evidence.ps1`, and successors). Re-asserting
   frozen hashes is meaningful in the same session that generated them; it is
   not required for every ordinary source commit, and a source change no
   longer obligates an immediate evidence regeneration cycle. This applies
   to `analysis/` records only; runtime trust regeneration after a worker
   rebuild remains mandatory (section 3).
3. **No new source-string grep tests.** New tests should exercise behavior
   (self-test routes, contract checks, compiled assertions) rather than
   assert substrings of source files. Existing grep tests are not deleted by
   this policy; they are candidates for staged replacement when their
   modules are next touched.

This repository has no CI. All of the checks above, including behavioral
self-tests and broker integration tests, currently run manually on developer
machines. The policy removes machine-bound hashes from the regression axis so
that future CI adoption becomes possible, but it does not claim that any
automation exists today.

## 6. Migration Guidance

- **New compatibility implementations** add a behavioral self-test route in
  the worker plus a focused contract test, following the
  `test_pf_pre_checkout_result.py` shape. Tests that need locally built
  artifacts are listed in `tests/local_artifact_tests.txt` so clean clones
  keep passing.
- **Evidence documents in `analysis/` are refresh-script territory.** Do not
  hand-edit identity fields to make a test pass; either run the refresh
  runner or leave the document dated as-is and rely on the behavioral tests.
- **Trust constants are always script-generated, never hand-patched.** After
  any local worker rebuild, run `tools/refresh-worker-trust.ps1` so the local
  broker accepts the local binaries; this is required for broker dispatch to
  work at all (section 3). A change that modifies worker source commits the
  trust constants regenerated from the build it validated with the mandatory
  broker integration tests. Because builds are machine-specific, every other
  machine regenerates locally after pulling; a trust mismatch there is an
  environment difference to resolve by regeneration, not by editing values,
  and does not require touching `analysis/` evidence.
- **Receipt volume is not a proxy for rigor.** A change needs the artifacts
  that its claims require, not one artifact per step. Prefer strengthening
  one behavioral test over adding another frozen document.

## 7. Out of Scope for This Document

- Deleting or rewriting existing evidence tests or `analysis/` documents.
- Changing broker admission behavior or worker isolation. The accompanying
  change moves the render/smart trust constants into generated files and adds
  their refresh script, but the admitted values and the fail-closed checks
  are unchanged.
- Relaxing the AE oracle identity contract; AE-dependent captures remain
  governed by `docs/AE_ORACLE_CROSS_MACHINE_RUNBOOK_2026-07-18.md`.
