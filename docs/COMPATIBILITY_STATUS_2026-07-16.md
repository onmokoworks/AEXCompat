# AEXCompat Compatibility Status (2026-07-16)

## Scope and status rules

This document summarizes the current host as an image-effect compatibility host. `Implemented` means that the current source publishes the relevant ABI and has focused local tests. It does not imply Adobe After Effects pixel equivalence. `Partial` identifies known semantic, slot, depth, or runtime-verification gaps. `Not implemented / unproven` is used whenever the available source, tests, or evidence do not prove compatibility.

Authoritative inputs for this snapshot are `minihost/src/l2_main.cpp`, the focused tests under `tests/`, and dated evidence under `analysis/`. Complete After Effects compatibility is not claimed. The project target is broader: every Effect AEX should at least be discoverable and diagnosable, and compatible effects should progress through parameter discovery and bounded image input/output without fixture-specific host branches. Unsupported host APIs must become reproducible compatibility findings rather than unexplained crashes.

## Current priority order

1. Expand the fixture corpus and run every Effect AEX through discovery, lifecycle, parameter, Classic, and Smart diagnostic stages; turn each reproducible missing Suite/slot or loader failure into a ranked compatibility task.
2. Install the verified three-probe oracle bundle with one explicit administrator operation, capture multi-matrix, Color, and Path Data observations, then remove the verified bundle.
3. Implement observed behavior without guessing undocumented ABI, beginning with failures affecting the largest number of distinct AEX binaries.
4. Add AE-oracle-backed normals/motion-vector coordinate and unit contracts, then exercise auxiliary channels with real effects.
5. Capture PF Batch Sampling availability and opaque batch-function behavior in AE, then implement observable lifecycle behavior without guessing private callable ABI.
6. Continue real-AEX and AE pixel-oracle matrices across depth, quality, masks, transfer modes, SmartFX, and GPU boundaries.
